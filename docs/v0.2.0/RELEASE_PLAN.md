切分判据：**release 的单位是「装上能看出差别的东西」，不是「一批做完的活」。** 原 A–F 六组按工作性质分组，不能各自成版——A 组（文档）产物零变化，F 组（验证发布）是每版都要做的动作。重切后每个版本都有一句用户能复述的价值主张。

代价：每个 release 要跑双平台打包 + 实机验证，切太细验证成本线性上升。三个是平衡点。

## 版本号决策

**`0.2.0`**（当前 `0.1.0`，无 tag，从未发布）

1. `electron/store/settings.ts` 的 electron-store migration 键写死为 `'0.2.0'`，注释为 "migrate from openclaw schema (v0.1.x) to cpa schema (v0.2.0)"。换号则该迁移失去意义。
2. 含新增能力与行为变更，非补丁级 → 1.0 前递增 minor。
3. `0.1.0` 从未发布，不存在需打补丁的存量用户。

### ⚠️ bump 的副作用

electron-store migration 以 `package.json` 的 `version` 为准。**版本停在 `0.1.0` 时那段 `'0.2.0'` 迁移永不执行**，目前是死代码；bump 的那一刻对所有现存 `settings.json` 首次生效。故 bump 必须配验证用例（见 TODO F9）。

### 推进约定（1.0 之前）

| 变更类型 | 递增位 |
|---|---|
| 新功能 / 行为变更 / schema 变更 | minor |
| 仅缺陷修复 | patch |
| 功能完整、双平台稳定、有真实用户 | → `1.0.0` |

`package.json` 的 `version` 在**发布日**才 bump，不在开发期：`electron-builder` 产出目录是 `release/${version}`，提前 bump 会让不完整构建冒充正式版；且上述迁移副作用应在受控时点触发。

## 为什么 0.2.0 是这个范围

`0.1.0` 的代码在 4 月完成自建 Agent 迁移，类型检查与单测全绿，但从未在真实安装包上端到端跑通。复盘发现问题不是「功能没写」，而是**「写了但没接线」**。

把不依赖 CPA 的那部分单独成版，好处是：网关重建期间**这个版本照样能做完、能发**。它也是三个版本里唯一能在当前阻塞下推进的。

### 🔑 G1 —— 网关恢复后重新评估

> **2026-09-12 更新**：CPA 已恢复，所以「引导页过不去导致 0.2.0 无法验收」这条理由**当下不再成立**——
> 现在全新安装能正常通过连接测试。G1 从「阻塞验收」降为「健壮性修复」。
> 但**建议仍留在 0.2.0**：网关是单台自建实例，刚刚宕了五个月，还会再宕；
> 下次宕机时所有新用户依旧被永久挡在门外。这正是过去五个月的教训本身。
> 若想更快发版，可把 G1 移到 0.3.0——这是范围取舍，不是技术障碍。

`src/onboarding/ConnectionStep.tsx:53` 是 `canProceed = testResult?.success === true`，配合 `onboardingGuard.needsOnboarding()`（`cpa.baseUrl` 或 `apiKey` 为空即强制引导）——**连接测试不通过，用户永远出不了引导页**。

后果有二：

1. CPA 重建期间，全新安装根本走不到桌宠界面，「装上就能看见桌宠」**无法验收**
2. 撇开本版本不谈，这个设计意味着**网关一挂，所有新用户被永久挡在门外**，连桌宠长什么样都看不到

改法：引导页增加「稍后配置」出口，允许进入主界面；桌宠可见可拖，聊天入口给出「未配置」提示。`needsOnboarding()` 相应改为只看 `onboarding.completed`。
