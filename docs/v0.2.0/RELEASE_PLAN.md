# v0.2.0 — 版本计划

> 制定于 2026-09-09 · 目标：**让 README 上写的每一条功能都真的能用，并产出第一个可分发的安装包**

## 版本号决策

**下一个版本 = `0.2.0`**（当前 `0.1.0`，无 git tag，从未发布过）

依据：

1. **代码里已经这么假设了。** `electron/store/settings.ts` 的 electron-store migration 键就是 `'0.2.0'`，注释写着 "migrate from openclaw schema (v0.1.x) to cpa schema (v0.2.0)"。换任何别的号都会让这段迁移逻辑失去意义。
2. 本轮范围包含新增能力（精灵资源、主动互动真正接线）与行为变更（气泡交互重做、日志开始落盘），不是补丁级改动 → 1.0 之前按 semver 惯例递增 minor。
3. `0.1.0` 从未发布，因此不存在需要打补丁的存量用户；`0.1.1` 没有意义。

### ⚠️ 一个必须知道的副作用

electron-store 的 migration 以 `package.json` 的 `version` 为准。**只要 `package.json` 停在 `0.1.0`，那段 `'0.2.0'` 迁移就永远不会执行**——它目前是死代码。把版本号 bump 到 `0.2.0` 的那一刻，迁移会对所有现存 `settings.json` 生效。因此 bump 必须配一条验证用例（见 TODO「发布」段）。

### 版本号推进约定（1.0 之前）

| 变更类型 | 递增位 | 例 |
|---|---|---|
| 新功能、行为变更、schema/migration 变更 | minor | `0.2.0` → `0.3.0` |
| 仅缺陷修复，无行为变更 | patch | `0.2.0` → `0.2.1` |
| 功能完整、双平台安装包稳定、有真实用户 | → `1.0.0` | — |

`package.json` 的 `version` **在发布日才 bump**，不在开发期。理由：`electron-builder` 的产出目录是 `release/${version}`，开发期就 bump 会让一堆不完整的构建产物冒充 `0.2.0`；且上面那条 migration 副作用应该在受控时点触发。开发期用本文件与 `docs/v0.2.0/` 目录标记目标版本即可。

## 本版本的目标

一句话：**把「看起来做完了」变成「装上就能用」。**

`0.1.0` 的代码在 4 月完成了自建 Agent 迁移，类型检查与单测全绿，但从未在真实安装包上端到端跑通过。停更 5 个月后复盘发现的问题不是「功能没写」，而是「写了但没接线」——日志模块从未被调用、chat 窗口收不到事件、桌宠没有精灵帧、主动互动不经过 Agent。`0.2.0` 就是把这些接线补齐并验证。

- 内部质量重构：IPC 常量表补齐、preload allowlist、`agent:final` 双解析器统一、`settings:set` 热更新
